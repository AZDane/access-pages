CVE-2026-107494 and CVE-2026-124709 — QUIC resource exhaustion.
The affected connection-ID retransmission and rejected-stream paths require an
OpenSSL QUIC endpoint. The exact Python binding selects TLS methods, and the
application uses Python TLS; its static Go services do not link OpenSSL. No
inventoried consumer imports a QUIC method. Existing runtime observations also
show no Python QUIC API. Neither affected protocol path is selected.
https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/107xxx/CVE-2026-107494.json
https://openssl-library.org/news/secadv/20261117.txt

CVE-2026-95690 — DTLS fragment reassembly allocation.
The same method/source review excludes DTLS: _ssl.c selects TLS_method,
TLS_client_method, TLS_server_method or legacy TLS-version methods, never a
DTLS method. No inventoried consumer imports DTLS entry points. Ordinary TLS
does not enter the datagram-handshake fragment reassembly path.
https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/95xxx/CVE-2026-95690.json

CVE-2026-84786 — DANE certificate/TLSA validation crash.
The exact Python binding and application do not enable OpenSSL DANE or supply
TLSA records. No external consumer imports SSL_CTX_dane_enable, SSL_dane_enable
or SSL_dane_tlsa_add. libssl itself imports X509_STORE_CTX_set0_dane; this
internal provider call is present, not overlooked, but the application never
configures the DANE state needed to reach the affected validation combination.
https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/84xxx/CVE-2026-84786.json

CVE-2026-35190 — Suite B TLS 1.3 key-share processing.
SSL_CTX_set_cert_flags is a macro through SSL_CTX_ctrl, which Python does import;
symbol absence alone cannot establish this decision. Reviewed _ssl.c does not
set Suite B certificate flags. OpenSSL ssl/ssl_ciph.c also sets these flags for
SUITEB-prefixed cipher strings: the application never calls set_ciphers or
accepts a cipher-selection input, and the pinned default cipher configuration
does not select Suite B. Both the macro and cipher-string paths are excluded.
https://openssl-library.org/news/secadv/20261117.txt

CVE-2026-107493 — caller-supplied PEM X509_INFO stack use-after-free.
No external consumer imports the PEM_X509_INFO_read family. In the exact
OpenSSL source, crypto/x509/by_file.c's CA-loading call and crypto/ts/ts_conf.c
pass NULL as the stack. The wrappers in crypto/pem/pem_info.c forward a caller's
stack but do not create a non-NULL caller on the application's behalf. Python
certificate loading does not supply an existing X509_INFO stack. Thus the
required non-NULL stack reuse after a failed read is absent.
https://openssl-library.org/news/secadv/20261117.txt

CVE-2026-121481 — EVP_EncodeBlock near-INT_MAX input overflow.
No external consumer imports EVP_EncodeBlock. Application base64 operations use
Python's binascii implementation, not OpenSSL's encoder. Internal OpenSSL
callers in crypto/pem/pem_sign.c, crypto/x509/x509spki.c and
crypto/http/http_client.c perform PEM signing, SPKI encoding or OpenSSL HTTP
proxy authentication; the reviewed Python application invokes none of these
APIs. Python SMTP/HTTP authentication uses Python base64. This decision excludes
the actual caller paths, rather than assuming OpenSSL's length arithmetic safe.
https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/121xxx/CVE-2026-121481.json

CVE-2026-121482 — CMS/PKCS#7 SignedData CRL-checking CPU exhaustion.
No inventoried consumer imports CMS or PKCS7 APIs, and neither the application
nor its Python TLS binding verifies CMS/PKCS#7 SignedData. Ordinary TLS X.509
verification is not this signed-message path. The OpenSSL CLI is absent.
https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/121xxx/CVE-2026-121482.json

The existing dynamic-loading/threat-model boundary below applies to all eight
decisions. Adding native bridges, custom cipher/protocol choices, a CMS consumer
or another executable invalidates the pinned review. Prefer vendor-fixed
packages when available; these assessments do not substitute for such fixes.

Threat model: remote application inputs through the existing fixed application
entry points. No arbitrary Python execution, attacker-provided extension module,
privileged container access, hostile replacement of application files or native
code, or untrusted custom image is covered. New source/imports, dependencies,
CLI operations, cipher/provider selection or changed advisory scope invalidates
the byte-pinned assessment. A successful exploit of another flaw allowing code
execution is not covered by an unreachable disposition.

CVE-2026-100290 — glibc regex allocation-failure cleanup.
Only libform/libformw import regcomp/regexec, and no inventoried ELF has a
DT_NEEDED dependency on those libraries. No packaged application imports curses
or a native bridge or dynamically loads form libraries. Python uses its own
regex engine. Source review of posix/regex.c, regcomp.c and regexec.c follows the
GNU re_compile_pattern/re_search/re_match families and legacy re_comp/re_exec.
Additional internal callers in stdlib/rpmatch.c and misc/regexp.c are reached
through rpmatch, step and advance; no inventoried consumer imports these either.
locale/programs/ld-messages.c is a localedef build-tool caller, not an application
entry point. The gate checks the expanded imported-symbol set and rejects new
form dependencies. This conclusion includes source/internal callers; it is not
based solely on the absence of regcomp/regexec in the application executable.
https://sourceware.org/bugzilla/show_bug.cgi?id=34991

CVE-2026-115819 — wide scanf narrow-buffer terminator overflow.
No inventoried ELF imports a wide scanf symbol, including ISO C99/C23 and long
double compatibility aliases. Source review follows the libio and wcsmbs entry
points, stdio-common/vfwscanf.c, and the long-double compatibility wrappers into
__vfwscanf_internal. stdio-common/vfscanf-internal.c builds separate narrow and
wide implementations under COMPILE_WSCANF; ordinary narrow scanf does not enter
the affected wide conversion. The other source references are declarations,
tests and compatibility entry points. No application native bridge or arbitrary
symbol lookup is permitted by the reviewed source. All ELF bytes and imports are
pinned; adding a wide-scanf consumer or changing a provider invalidates the review.
https://sourceware.org/bugzilla/show_bug.cgi?id=34989

Dynamic-loading boundary for both glibc decisions: the packaged application
does not import ctypes/cffi, enable SQLite extensions, supply native modules,
select external OpenSSL providers, or set attacker-controlled loader options.
Python's extension loader and the native libraries retain dynamic-loading
capability, so arbitrary code execution or hostile replacement configuration is
explicitly outside this application-input assessment. These are unreachable
dispositions, not removal or patching of glibc code.
